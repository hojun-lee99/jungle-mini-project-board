요구사항 정의서(v2)

## 1. 프로젝트 개요

Jungle Whiteboard는 개인별 다수의 보드를 제공하고, 개인은 다른 사용자와 보드 내용을 공유할 수 있는 웹 기반 협업 시스템이다.

사용자는 자신이 접속한 보드에서 텍스트 및 이미지를 포함한 포스트잇을 생성하고, 자신이 생성한 포스트잇 내용을 수정하거나 위치를 이동하며 관리할 수 있다.

보드의 생성자가 보드의 관리자가 되며 보드 내의 모든 포스트잇에 대해 CRUD를 할 수 있다.

보드의 public_id를 알고 있는 사용자는 보드를 조회(Read)할 수 있다.

private 보드 옵션을 제공하지 않는다

생성자가 보드를 은닉 방법은 보드 링크를 타인과 공유하지 않는 것이며, 보드의 생성자는 언제든지 보드의 public id 를 바꿀 수 있다.

# 2. 사용자 요구사항

## 2.1 회원 기능

- 사용자는 회원가입 및 로그인을 할 수 있다.
- 회원가입 시 다음 정보를 입력한다:
    - username (작성자 표기용 이름)  *user_id는 별도의 UUID 사용
    - password
- 로그인한 사용자만 포스트잇 생성/수정(이동 포함)/삭제가 가능하다.
- 로그인한 사용자는 로그아웃할 수 있다.
- 로그인한 사용자는 '보드 만들기 / 내가 만든 살아있는 보드 목록 열람 / 나에게 귀속된 보드 스냅샷 열람' 을 할 수 있다.
- 모든 사용자는 '개별 사용자가 공개하기로 전환한 모든 보드 스냅샷을 모아놓은 게시판'을 열람할 수 있다.
- 로그인한 사용자는 자신이 생성한 보드에 있는 모든 포스트잇에 대해 CRUD를 할 수 있다.

## 2.2 회원가입 유효성 검사

- 이름(username): 2자 이상 20자 이하. 영문 대소문자, 숫자, 한글, `_` 만 허용.
- 비밀번호(password): 8자 이상 50자 이하. 영문 대소문자, 숫자, 특수문자 `!@#$%^&*()-_` 만 허용.
- 이름 중복 불가.

# 3. 보드 기능

## 3.1 보드 구조

- 보드는 로그인한 사용자가 생성한다.
- 보드의 내용은 실시간으로 수정된다.
- 보드는 public_id(UUID)를 갖는다.(익명의 사람 열람 가능)
- 보드 삭제시 스냅샷(이미지)을 시스템에 저장한다. 해당 이미지는 연관된 사용자만 열람 가능하다.

## 3.2 접근 권한

- 본 시스템은 협업 실험용 구조로, 보드 단위의 쓰기 권한 제한 기능은 제공하지 않는다.
- 로그인한 사용자는 자신이 생성한 보드를 CRUD 할 수 있다. (보드에 있는 모든 포스트잇에 대해서도 CRUD 가능)
- 로그인한 사용자는 자신이 생성한 보드의 public_id를 수정할 수 있다.
- 로그인 사용자는 public_id를 알고 있는 보드에 한하여 쓰기 작업을 수행할 수 있다.

## 3.2. public id 변경시 조치

-> 보드 생성자가 public_id를 변경하면, 서버는 기존 public_id에 접속 중인 모든 클라이언트에게 board_invalidated 이벤트를 전송한다. 클라이언트는 이를 수신하면 WebSocket 연결을 종료하고 메인 페이지로 리다이렉트한다. 또한 기존 public_id에 대한 모든 HTTP 요청은 404/410으로 거부한다.

- 생성자가 보드의 public id 를 바꿀 경우 해당 보드에 접속 중인 모든 접속자는 websocket이 끊기고 메인 페이지로 리다이렉트된다.
- public_id 변경은 해당 보드의 접근 링크를 무효화한다.
- 변경 즉시, 서버는 기존 public_id room에 있는 모든 클라이언트에게 “board_invalidated” 이벤트를 브로드캐스트한다.
- 클라이언트는 이벤트 수신 시:
	- WebSocket 연결 해제
	- 보드 페이지 접근을 중단
	- 메인 페이지로 이동(redirect)
- 모든 보드 관련 API/페이지는 항상 최신 public_id 기준으로 검증해야 한다.(DB에서 public_id가 현재 값인지 확인하고 아니면 404 또는 410(Gone) 으로 거부)

# 4. 포스트잇 기능

## 4.1 생성

- 텍스트 및 이미지가 포함된 포스트잇을 생성할 수 있다.
- 텍스트는 최대 500자까지 입력 가능하다.
- 보드당 최대 300개의 포스트잇을 허용한다.(초과된 상태에서 일부 삭제되면 다시 생성 가능하고, 동시 생성으로 인해 일시적으로 300개를 초과할 수 있으나 이후 생성 요청은 실패 처리한다.)

## 4.2 수정 및 삭제

- 일반 사용자는 자신이 생성한 포스트잇만 수정/이동/삭제할 수 있다.
- 단, 보드 생성자는 해당 보드의 모든 포스트잇에 대해 CRUD 가능하다.

## 4.3 이동

- 포스트잇은 마우스 드래그로 이동할 수 있다.
- 이동은 보드 생성자와 포스트잇 작성자만 가능하다.
- 포스트잇은 보드 영역을 벗어날 수 없다.
- 포스트잇은 서로 겹칠 수 있다.

## 4.4 표시 규칙

- 포스트잇에는 최소/최대 크기가 존재한다.
- 텍스트가 영역을 초과하면 말줄임표(`...`)로 표시한다.
- 이미지가 영역을 초과하면 비율을 유지한 채 자동 축소된다(CSS 기반).
- 포스트잇 클릭 시 전체 텍스트 및 원본 이미지를 모달 창에서 표시한다.
    - 클릭한 포스트잇이 일시적으로 사용자의 보드에서 가장 위로 올라온다.(프론트단에서 해결)
    - 전체 텍스트 표시
    - 원본 이미지 표시 (max-width: 90vw, max-height: 80vh)
    - 모달에서는 작성자 본인일 경우 수정 버튼이 활성화된다.
- 우측 윙바에서 자신의 포스트잇 목록을 조회할 수 있다.
- 윙바에서 항목 클릭 시에도 동일한 모달 UI를 재사용한다.
- 사용자가 수정 저장 또는 이동 저장(PATCH 성공) 시 해당 포스트잇은 모든 사용자에게 최상단으로 반영된다.
- 포스트잇 클릭 시 일시적으로 최상단에 보이는 것은 로컬 UI 효과로만 처리한다.

### 4.4.1 z-index 정책

- 포스트잇은 겹칠 수 있으며, 화면에서 위/아래 표시 순서는 'z_index'로 결정한다.
- 'z_index'는 보드 단위로 관리된다. (같은 보드 내에서만 비교 의미가 있다.)
- 다음 동작이 성공(PATCH/POST 성공)했을 때, 해당 포스트잇의 'z_index'는 해당 보드의 현재 최대값보다 1 큰 값으로 갱신된다:
  - 포스트잇 생성
  - 포스트잇 수정 저장
  - 포스트잇 이동 저장(드래그 종료 후 저장)
- 동시 요청으로 인해 'z_index'가 중복되지 않도록, 서버는 보드 단위 카운터를 사용하여 'z_index'를 원자적으로 처리해야 한다.
- 포스트잇 클릭 시 “일시적으로 최상단에 보이는 효과”는 로컬 UI 효과이며, DB의 'z_index'를 변경하지 않는다.

# 5. 이미지 관련 요구사항

## 5.1. 이미지 업로드 요구사항
- 허용 확장자: jpg, jpeg, png, gif
- 최대 업로드 용량: 3MB
- 이미지 파일만 업로드 가능(이미지 업로드는 서버로 multipart 업로드를 수행한다.)
- 포스트잇 삭제 시 이미지도 함께 삭제 시도한다(실패해도 DB 삭제는 진행).

## 5.2. 보드 스냅샷 이미지 요구사항
- 보드 삭제시에 보드의 최종 스냅샷을 이미지로 보전하여 보드를 생성한 사용자에게 귀속시킨다.
- 스냅샷은 생성 직후에 귀속한 사용자 외에는 볼 수 없다.
- 사용자는 자신에게 귀속된 스냅샷의 공개 여부를 토글로 전환할 수 있다.
- 사용자는 시스템에 존재하는 모든 보드 스냅샷 중 공개된 스냅샷 게시판에 접속하여 이를 열람할 수 있다.

# 6. 동시성 요구사항

- 포스트잇 수정(이동 포함)은 낙관적 락 방식을 사용하여 먼저 수정한 요청만 반영한다.
- 수정 요청 시 클라이언트는 “내가 봤던 버전(version)”을 함께 보낸다.
- 서버는 version 불일치 시 409(Conflict)로 거부한다.
- 409 발생 시 클라이언트는:
    - 최신 데이터 재조회
    - 사용자 변경사항 롤백
    - 안내 메시지 표시
- WebSocket은 데이터 정합성을 보장하지 않는다.
- 모든 수정 요청은 반드시 HTTP PATCH를 통해 처리한다.
- 서버는 version 검증 및 DB 업데이트 성공 이후에만 WebSocket broadcast를 수행한다.
- version 충돌(409) 발생 시 WebSocket 이벤트는 발생하지 않는다.
- 보드 생성자가 public_id를 변경한 이후에 도착한 모든 HTTP 요청(PATCH/POST/DELETE 포함)은 실패 처리한다.
- 서버는 요청에 포함된 public_id가 현재 DB에 저장된 최신 public_id와 일치하는지 항상 검증해야 한다.
- public_id가 일치하지 않을 경우 해당 요청은 404 또는 410(Gone)으로 거부한다.
- public_id 변경 이전에 처리 완료된 요청만 유효하다.

# 7. 비기능 요구사항

- 데이터 저장은 MongoDB를 사용한다.
- 로그인 사용자만 쓰기 작업 가능
- 서버는 클라이언트 입력을 신뢰하지 않으며, 권한 검증은 서버에서 수행한다.
- 보안 우회를 방지해야 한다.
- 3일 프로젝트 범위 내에서 구현 가능해야 한다.

---

# 8. 실시간 동기화 요구사항

- 여러 사용자가 하나의 보드에서 동시에 서로 다른 메모를 실시간으로 수정이 가능해야 한다.
- 하나의 보드에 최대 100명이 동시 접속해서 보고 있을 수 있어야 한다.
- WebSocket 사용
- 익명 사용자는 SSR 기반 조회만 가능하며, 실시간 동기화(WebSocket broadcast)의 대상이 아니다.

- soft delete(기본은 물리삭제)
